# Crypto64 — обзор безопасности (2026-08-19)

Объект: `bbcp/Crypto` (= bbext/Crypto64, 64-битный порт bbext/Crypto).
Метод: чтение исходников + прогон тестов (все зелёные) + адресные пробы
(Probe63-69: граничные случаи 64-битных примитивов). Фокус: TLS-клиент,
ГСЧ, примитивы. Это обзор именно кода, а не пенетрационный тест.

## КРИТИЧНЫЕ

### 1. TLS: подпись ServerKeyExchange не проверяется (MITM)
`CryptoTLS.ReceiveServerKeyExchange` (TLS.odc): публичный ключ ECDHE
принимается, подпись сервера читается и… рядом стоит `(* TODO CHECK
SIGNATURE *)`. Подпись не проверяется. Активный MITM подменяет ключ x25519
на свой и расшифровывает весь трафик. Фикс: RSA PKCS#1 v1.5 verify
(SHA256) по параметрам ECDHE — все примитивы есть (CryptoRSA, CryptoSHA256,
CryptoPKCS1).

### 2. X.509: цепочка и hostname не проверяются вообще (MITM)
- `CryptoTLS` НИГДЕ не вызывает `CryptoX509.Verify` — сертификат сервера
  принимается как есть.
- `CryptoX509.CheckSignature` — заглушка `RETURN TRUE`.
- Проверки hostname (CN/SAN) нет вовсе; SNI шлём, но ответ не сверяем.
- `X509.Verify` имеет флаги `AllowNotTrusted/AllowOutdated/Bypass` —
  с Bypass сразу TRUE.
Итого: подделанный/самоподписанный/чужой сертификат принимается молча.
Фикс: проверка цепочки подписей до доверенного корня, сроков и hostname;
хранилище корневых CA.

### 3. Удалённое переполнение буфера в ReceiveServerKeyExchange
`sigLen` читается из сети (2 байта, до 65535) и копируется в
`signature: ARRAY 512` без проверки: `FOR pos := 0 TO sigLen-1 DO
signature[pos] := data[...]`. sigLen > 512 — запись за границу буфера.
Вредоносный сервер получает запись в стек кадра. Фикс: ASSERT(sigLen <= 512)
до копирования (и валидация len от записи TLS).

### 4. Парсинг входящих через ASSERT = удалённый DoS
Всё чтение handshake (`ASSERT(data[ofs] = 03X)` и т.п.) доверяет байтам
сервера. Любое отклонение — HALT процесса. Сервер (или MITM) роняет клиента
одним пакетом. Фикс: возвраты ошибок вместо ASSERT на сетевых данных.

## ВЫСОКИЕ

### 5. Слабая энтропия ГСЧ → предсказуемые ключи
`CryptoFortunaRng` собирает энтропию из `Services.Ticks()` и статистики кучи
(`DevHeapSpy.par.*`), `CryptoAosRandom` — LCG, сидируется тиками
(`SELF.rand.InitSeed(SHORT(Services.Ticks()))`). `/dev/urandom` не
используется. Ключи X25519/RSA/DH и сессионные ключи TLS предсказуемы
для наблюдателя, знающего примерное время запуска. Фикс: источник
энтропии из `getrandom(2)`/`/dev/urandom` через LinLibc, плюс существующие
пулы Fortuna как дополнение.

## СРЕДНИЕ

### 6. Дефолтный набор suites устарел
`TLS.InitDefaults`: ECDHE_RSA_AES128_CBC_SHA256, RSA_AES128_CBC_SHA,
RSA_3DES_EDE_CBC_SHA, ECDHE_RSA_AES128_GCM_SHA256. Замечания:
- RSA key-transport (без forward secrecy) в дефолте;
- 3DES-CBC (Sweet32) в дефолте;
- CBC-suites = MAC-then-encrypt (класс Lucky13);
- политика допускает RC4/MD5/NULL-suites (в дефолте не предлагаются).
Фикс: дефолт = только ECDHE + GCM; 3DES/RC4/NULL убрать из политики.

### 7. Неконстантное время в bignum и RSA/ECDH
`CryptoAosBigNumbers` (Div2/mul/ModExp) — data-dependent ветвления/циклы;
RSA (PKCS1) и X25519 операции с секретами не constant-time → тайминговые
утечки (локальный/сетевой с высоким разрешением атакующий). Для нашей
модели угроз (локальная дев-система) — приемлемо, для серверного
использования — нет.

## ЗАМЕТКИ / INFO

- X25519: clamping корректен (248/127/64), тесты Generate/Agreement/
  FromPrivateKey зелёные.
- Хэши/HMAC/шифры — по эталонным векторам зелёные.
- GCM (AEAD) реализован и проходит тесты.
- Клиентская часть TLS only (серверной нет) — поверхность меньше.
- `CryptoAosStreams.Net64` сериализует 64-бит значения десятично (1e8) —
  значения ≥ 1e16 теряют старшие биты (не секьюрити, но корректность).

## Приоритет исправлений

1. sigLen bounds-check (п.3) — одна строка, закрывает удалённую запись в память.
2. Подпись ServerKeyExchange (п.1) — primitives есть, работа на день.
3. X509: hostname + цепочка (п.2) — самая большая работа.
4. getrandom энтропия (п.5) — небольшая.
5. Политика suites (п.6) — одна правка InitDefaults.
