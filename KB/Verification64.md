# Верификация при портировании на 64 бита: анализ и стратегия

(Сессия 2026-08-09. Обстоятельства: серия GC-крашей при компиляции
модулей с большими sym-файлами; каждый краш требовал многочасовой
gdb-археологии. Пользователь попросил осмыслить процесс через Дейкстру
("A Discipline of Programming") и Вирта.)

## 1. Почему отладка съедает столько времени

Корневые причины всех найденных багов — СИСТЕМАТИЧЕСКИЕ ошибки порта
32→64, но проявляются они далеко от места нарушения:

| Баг | Нарушение инварианта | Где всплыло |
|-----|----------------------|-------------|
| двойной push FPU-параметра | callee видит size=b+tsize | SEGV в ThisFinObj, много вызовов спустя |
| SHORT(gregs[RSP]) в трапе | стек > 2ГБ не влезает в INTEGER | SIGFPE-каскад в HandleTrap |
| sliver-absorb a=16 | цепочка блоков не тайлится | Next читает tag=0 через ~2000 блоков |
| Mark на free-блоке | tag ≠ дескриптор в модульной памяти | DSW падает по мусорному offset |
| Int32-глобал как r64 | загрузка по form, не по размеру слота | запись candidates[мусор] — в другом месте |

Общая структура потерь времени:

1. **Запаздывание сигнала.** Нарушение инварианта (куча, кодеген) и крах
   разделены тысячами операций. Это ровно то, о чём Дейкстра: программа
   без доказательства "не имеет права на существование" — у нас не было
   исполняемой формулировки инварианта, поэтому первым "доказательством
   неправильности" становился SIGSEGV.
2. **Инварианты существуют, но не записаны.** Тайлинг цепочки блоков,
   согласие stride между [code] Next и NewBlock, "tag указывает в
   модульную память" — всё это зналось устно и проверялось вручную
   gdb-скриптами ПОСЛЕ краха.
3. **[code]-процедуры обходят язык.** Next в байтах — вне типовой
   системы; его согласие с NewBlock ничем не enforced. Дейкстра: текст
   программы должен позволять вывести predicate transformer — у [code]
   его нет.
4. **Неявные 32-битные допущения.** SHORT()/INTEGER вокруг адресов,
   dword-загрузки указателей — не видны в типах, находятся по краху.
5. **Два аллокатора, две дисциплины.** Kernel64 bump vs CP Kernel
   кластеры — инварианты разные, Mark/Sweep покрывают только одну.

## 2. Что из Дейкстры/Вирта применимо БУКВАЛЬНО

- **wp-семантика → исполняемые инварианты.** Постусловие NewBlock и
  Sweep — "блоки тайлят [c+24, end) и free-list согласован с цепочкой".
  Записать это один раз как Kernel.ValidateHeap и вызывать — это и есть
  "proof goes hand in hand with program", только executable.
- **Guarded commands → отказ от скрытых else.** Каждая ветвь в GC
  (free/absorb/insert/exact) должна иметь явное условие и ASSERT на
  невозможное. absorb a=16 жил именно как неявный else.
- **Loop invariants.** Mark (DSW) и sweep-циклы — места для явных
  инвариантов цикла (tag = дескриптор+flag; blk внутри [c+24, end)).
- **Вирт: простота и типизация.** Адрес ≠ INTEGER. Один аллокатор.
  Один источник формулы stride.
- **Тестирование показывает наличие ошибок, не отсутствие** — поэтому
  цель: каждый класс бага превращать в (а) инвариант с ASSERT в
  программе, (б) self-test при старте, (в) probe в регрессионный набор.

## 3. Стратегия (принято: НЕ переписывать систему на новых принципах)

Оценка: архитектура BB (модули, MVC, GC с DSW) сама по себе виртовская
и здоровая; баги — семантика порта, не дизайн. Переписывание потеряет
30 лет проверенного поведения. Путь — добавить верификационный слой:

A. **Kernel.ValidateHeap*** — ходит кластеры и проверяет:
   - тайлинг: сумма stride == end-c-24; stride == формуле Next;
   - free-блоки: tag = ADR(size), total = size+8 ≡ 0 (mod 16), ≥ 32;
   - live-блоки: tag-flag ∈ модульной памяти, ~InHeap;
   - free-list: каждый элемент — free-блок цепочки, размеры совпадают,
     цепочки без циклов.
   Вызывать: из Collect/Sweep в debug-режиме, и как команду
   `Kernel.CheckHeap` для smoke-тестов. Цена вопроса: крах п.75/76
   ловился бы ASSERT'ом в момент нарушения, а не через 2000 блоков.
B. **Единая формула stride.** Одна PROCEDURE Stride(size, isArray): —
   ей обязаны следовать NewBlock, [code] Next, Sweep, MakeFree*.
   Boot-selftest: NewBlock известных размеров → Next → сравнить.
C. **Boot self-tests (контракты как исполняемые спеки).** При старте
   (debug): покрыть границы a ∈ {0, 16, 32}, absorb-случаи, массивы
   1/2/4/8-байтных элементов, финализаторы. ASSERT номер = номер контракта.
D. **Уровни ASSERT.** Номерные ASSERT остаются в проде (дёшево относительно
   GC). FinChainHit + 30/31/32 уже окупились — оставить навсегда.
E. **Кодеген: верификация эмиссии.** Класс бага "REXW для Int32":
   peephole-проверка в CPLamd64 — после эмиссии mov проверять
   согласие form/REXW (debug-ASSERT в самом компиляторе); регрессия:
   набор probe-модулей (Probe5-7 и др.) + сверка паттернов дизасма.
F. **Ликвидация 32-битных остатков.** grep-аудит: SHORT( вокруг адресов,
   S.VAL(INTEGER, *указатель*), dword-загрузки pointer-полей в [code].
   Завести список в KB и вычистить.
G. **[code]-процедуры → CP.** Next уже доказано работает по формуле —
   переписать на CP (FPU-int64 материализация теперь чинена), байты
   оставить только если CP медленнее (замерить). Каждая [code] =
   потенциальный рассинхрон со спекой.

## 4. Улучшения воркфлоу (принятые уроки)

- gdb-реконструкция GC-хода по post-mortem памяти — работает (Mark
  восстанавливает tag; блоки ≡ 8 mod 16). Шаблоны в /tmp перенести в
  tools64/gdb/ как постоянные скрипты (walk.py, watch-life.py).
- probe-модули (маленькие .cp в bbcp64use + ConsCompiler64.Compile) —
  быстрый изолятор err-кодов и крашей компилятора. Держать Probe*.cp
  вне дерева (в bbcp64use), удалять после.
- "1 unpatched sentinel slots" от лоадера — НЕ игнорировать: это
  признак непропатченного rip-relative глобала (см. вывод в логе Probe3).
- Перед gdb-археологией сначала: Kernel.CheckHeap (п. A) — 80% случаев
  локализует без gdb.

## 5. Открытые вопросы для следующих сессий

- Почему live-объект DevCPT (B=0x6003f9c0, type @0x42aa28a0, size 0x88)
  не был помечен (use-after-free после Sweep)? Гипотеза: ptroffs типа A
  не покрывает поле-ссылку (баг эмиссии дескриптора 64-бит) или ссылка
  идёт через путь, отрезанный guard'ом. Проверить ptroffs типа A vs
  фактический offset поля.
- "unpatched sentinel slots" — найти слот, проверить влияние.
- Orphaned free-блоки (chain-free, не в free-list) — норма после
  consume или утечка? Замерить после ValidateHeap.

## 6. Сессия 2026-08-16/17: два бага КОДОГЕНА — разбор по Дейкстре

### 6.1 Что случилось (симптомы → корни)

| Симптом | Корень | Нарушенный инвариант |
|---|---|---|
| Help→Contents: ASSERT(bar=NIL,100) | Int64-конст value-параметр: 2 qword вместо 1 (п.108) | caller кладёт ровно padr-16 байт; callee делает ret (padr-16) |
| Help→About: SEGV addr=3 в Utf8ToString | THISARRAY value-парам: conv→Stk + безусловный Push = дуп (п.109) | то же самое: число push перед call == числу слотов callee |

ОБА бага — нарушение ОДНОГО инварианта: **соглашение о вызове**
(caller и callee должны согласовать число и раскладку слотов).
Оба унаследованы от i386-мира, где push=4 байта и Int64=пара регистров.

### 6.2 Почему снова потрачено много времени

1. **Симптом далеко от причины — в другом модуле и другом слое.**
   Краш в Utf (жертва), причина в CPCamd64/CPVamd64 (источник).
   Дейкстра, гл.3: семантика программы = начальные состояния, для
   которых она достигает цели. Мы наблюдали финальное состояние
   (крах) и искали weakest precondition руками.
2. **Инвариант соглашения о вызове нигде не записан и не проверяется.**
   В CPC486/CPCamd64 нет ни одного ASSERT вида "число пушей == padr".
   Каждая процедура эмиссии (Param, Push, PushAdr, VarParDynArr)
   имеет негласные пре/постусловия на состояние Item (mode/form/reg/
   index/offset/scale/typ/tmode — 8 полей!). Комбинаций mode×form
   десятки; легальные нигде не перечислены.
3. **Ошибка в генерируемом коде не видна до исполнения.** Компилятор
   молча эмитит дурной код. Дейкстра, гл.1: "цель — чтобы текст
   программы и доказательство шли рука об руку". У нас текст (эмиттер)
   есть, а проверки результата нет.
4. **Длинный цикл обратной связи:** правка компилятора → go32 (пересборка
   кросс-компилятора!) → go64 пробника → дизасм. Забыть go32 — и мир
   компилируется старым багом (уже ловили).
5. **Трап-репортер сам падает** (StdDebug SEGV при печати трапа,
   рекурсия на одном PC) — вторичный сигнал глушится.

### 6.3 Что РЕАЛЬНО ускорило (зафиксировать как практику)

- **Probe-модули как изоляторы** (ObxProbe21/22/23): минимальный
  пример, воспроизводящий подозрение; компилируется за секунды,
  дизассемблируется целиком. Это "алгоритм вместо зазубривания ответов"
  (Дейкстра, гл.0): probe проверяет КЛАСС входов, а не один случай.
- **Сравнение caller vs callee дизасма** — сразу делит пространство
  поиска пополам. В п.108 callee был прав с первого взгляда.
- **Сравнение с 32-битным эталоном** (тот же вызов в bbcb2 .ocf,
  objdump -m i386): 5 чистых push в CPC486 против 6 в CPCamd64 —
  diff генерации вместо чтения 2000 строк компилятора.
- **Трассировка компилятора принтами (mode/form) в ActualPar/expr** —
  одна итерация даёт факт "ap.mode=Stk", который статическим чтением
  искался часами. НО: чистка принтов сломала CPB (потерян IMPORT) —
  отладочные правки надо делать ОДНИМ откатываемым патчем (git stash /
  отдельная ветка debug/), не ручным вычитыванием.
- **gdb-хелперы работают только с unstripped bbrun64** (modlist).

### 6.4 Дейкстра → конкретные механизмы для кодгена

A. **Инвариант соглашения о вызове — проверять МЕХАНИЧЕСКИ.**
   Инструмент tools64/verify-callconv.py: для каждой экспортированной
   процедуры модуля взять N из `ret N`; для каждого call-сайта в мире
   посчитать слоты между восстановленным rsp... Проще (v1): для набора
   probe-модулей сравнивать "push-и перед call" с "ret N" callee.
   Это исполняемая формулировка инварианта — запускать после каждой
   правки CPCamd64/CPVamd64 как регрессию.
B. **Постусловия на эмиссию (ASSERT в компиляторе).**
   - Push(x): PRE x.mode # Stk (иначе дуп) — ловить ASSERT'ом при
     компиляции, а не SEGV в рантайме. Уже частично стоит в Param
     (Pointer-ветка) и теперь в ActualPar thisarrfn.
   - Param(par, ap): POST "на стеке ровно ParSize(par) байт с момента
     входа" — реализуемо: запомнить счётчик эмитированных байт стека,
     сверить. DevCPLamd64 уже ведёт стек-учёт для FPU (IncStack/
     DecStack) — распространить на машстек.
   - expr(n, x): POST "x.mode IN {допустимые для n.typ.form}" —
     таблица легальных (mode × form) одним ASSERT в конце expr.
C. **Item-инварианты (Вирт: запись — это инвариант).** Задокументировать
   в CPLamd64 над TYPE Item: для каждого mode, какие поля значимы
   (напр. Reg: reg=lo, index=hi ТОЛЬКО для Int64; Con Int64: offset=lo,
   scale=hi; Stk: значение на [rsp]). Без этого каждая правка
   угадывает семантику полей заново.
D. **Радикальное упрощение (отложено, но записать): Int64 в ОДНОМ
   64-битном регистре.** Текущая модель Int64 = пара lo/hi (reg/index)
   — наследие i386, где 64 бита не влезали в регистр. На amd64 влезают.
   Убрав парность, исчезают: LongAdd/LongSub/LongCmp, MakeLongHi,
   FreeHi, LoadLong, PtrToLong/LongToPtr, половина ConvMove, баги
   класса п.108/п.109. Это Виртовское "убрать понятие целиком".
   Риск: большая переработка CPCamd64 + пересборка мира; делать ПОСЛЕ
   того, как мир стабильно работает и покрыт probe-регрессией.
E. **Один компилятор — один источник истины.** Сейчас CPC486 (i386) и
   CPCamd64 — две ветви одного кода; каждый баг надо проверять дважды.
   Раз 32-бит legacy можно выкинуть (решение пользователя) — CPC486/
   CPL486/CPV486 выводятся из дерева сборки, чтобы не тратить внимание.

### 6.5 Ответ на вопрос "не построен ли компилятор слишком сложно"

Архитектура CPB/CPV/CPC/CPL/CPE (frontend → деревья → item-машина →
эмиссия) — стандартная виртовская декомпозиция и сама по себе виновата
мало. Сложность взрывается на СТЫКАХ: (1) неявные преобразования типов
фронтендом (conv-узлы с pseudo-типами типа intrealtyp, вставляемые
непрозрачно — см. ненайденного создателя conv в п.109), (2) item-
машина с 8-полем состоянием без записанных инвариантов, (3) две
целевые архитектуры в одном коде. Вывод: НЕ переписывать (потеряем
30 лет поведения), а: выкинуть i386-ветвь (D), записать инварианты
(C), добавить исполняемые проверки (A, B). Это и есть "separation of
concerns" (Дейкстра, гл.27): сначала забыть про рантайм и чинить
кодеген как самостоятельную задачу с собственной спецификацией.

### 6.6 Открытые вопросы (добавлены 2026-08-17)

- КТО создаёт conv-узел (typ=intrealtyp) вокруг adr-аргумента
  THISARRAY: CPB.Convert инструментирован и НЕ создаёт; узел появляется
  между CPB.StPar1 (там left = чистый adr, проверено принтом [ST1]) и
  кодогеном. Кандидаты не подтвердились: CheckBuffering (нет для Undef),
  CheckVarParBuffering (нет для Ndop), CPP (не создаёт Nmop).
  Прагматично закрыто стражем Stk; найти создателя — при следующем
  related баге.
- free(): invalid pointer при выходе из GUI (libc) — вероятно
  двойное освобождение/чужой указатель в финализаторах GTK-объектов.
- StdDebug (трап-репортер) падает при печати трапа (SEGV внутри,
  рекурсивный трап на PC=Kernel+0x257 addr=0x18) — сделать минимальный
  надёжный репортер до того, как понадобится снова.
- About-диалог: поля Version/Build не подставлены (appVersion и т.п.).
