# Отчёт: зачем мы меняли выравнивание (простым языком)

## Проблема

BlackBox вызывает функции C-библиотек (libc, GTK, сокеты). Данные между ними
ходят через структуры в памяти. C и наш компилятор должны **одинаково**
раскладывать поля структуры по адресам — иначе один пишет в одно место,
другой читает из другого.

C на 64-битном Linux раскладывает поля по «естественному» правилу: 8-байтное
поле (указатель, long) встаёт на адрес, кратный 8. Если перед ним пять
4-байтовых int (20 байт), C вставит 4 байта паддинга, и указатель ляжет на 24.

Наш компилятор пришёл из 32-битного мира, где всё выравнивалось по 4. Он
клал тот же указатель на 20. Когда glibc писала адрес по 24, а мы читали по
20 — получали мусорный указатель и падение. Так сломался getaddrinfo → не
работала загрузка пакетов в Paket (и любой интернет по имени хоста).

## Почему нельзя было просто переключить всё на 8

Попробовали — сломался весь BlackBox. Причина: у системы есть **свой**
формат файлов (OCF — объектные файлы модулей), где метаданные лежат плотно,
по 4-байтному правилу. Ядро читает эти блоки теми же CP-записями. Поменяв
глобальное правило, мы разъехались с собственным форматом: ядро перестало
находить экспортированные процедуры («command not found», мёртвая консоль).

Причём придумать запись, которая читалась бы одинаково при обоих правилах,
для части формата невозможно (массив 8-выравниваемых структур после
4-байтового счётчика по-разному встаёт при разных правилах, а пометить
запись двумя атрибутами сразу язык не даёт).

## Итоговое решение

Два мира разведены явно:

- **Свой формат (OCF, метаданные)** — остаётся на старом правиле pack-4.
  Ничего не ломается.
- **Чужой формат (структуры C-библиотек)** — помечается в исходнике
  `[align8]`, и компилятор для этих записей применяет правило C. Так помечены
  `addrinfo` и `sockaddr_storage` в LinNet. Часть структур (LinLibc) уже была
  аккуратно разложена руками с явными pad-полями — они одинаково правильны
  при любом правиле, их не тронули.

Попутно `Kernel.BootInfo` (структура, которую C-загрузчик bbrun64 заполняет
вручную по смещениям) переставлен так, чтобы паддинга не было при любом
правиле — больше никакой зависимости от компиляторного дефолта.

## Правило на будущее (для новых FFI-биндингов)

1. Раскладку C-структуры сверять с заголовком (offsetof), не гадать.
2. Если после 4-байтных полей идёт 8-байтное — либо `[align8]`, либо явный
   pad (смотри примеры в LinLibc: sigaction_t, stack_t).
3. Проверять чтение ПОСЛЕДНИХ полей структуры, а не только первых.
