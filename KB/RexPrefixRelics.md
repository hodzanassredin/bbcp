# REX-prefix relics: однобайтовые inc/dec (40H-4FH) в 64-битном кодогене

## Суть

В x86-32 опкоды 40H-4FH = однобайтовые `inc r32`/`dec r32`. В x86-64 это
REX-префиксы (40-4F = REX, REX.X/B/R/W комбинации). Байт, скопированный из
32-битного бэкенда, НЕ выполняет inc/dec, а молча превращается в префикс
следующей инструкции — меняет её операнды (напр. `or al,al` -> `or al,r8b`).

Симптомы коварны: инструкция не падает, а работает неправильно. `46 08 C0`
(or al,r8b вместо or al,al) — цикл копирования строки никогда не видит NUL,
пишет 7КБ+ в стековый буфер -> SIGSEGV далеко от источника (stos на вершине
стека). `49` перед jne -> REX.WB на jne (безобидно с виду, но dec ecx не
выполняется — счётные циклы не завершаются по счётчику).

## Найденные места (исправлены, bbcp blackbox20)

Dev/Mod/CPLamd64.odc.txt:
- `GenStringMove`: 46H (inc esi), 2×4FH (dec edi), 49H (dec ecx) ->
  `48 FF C6` (inc rsi), `48 FF CF` (dec rdi), `FF C9` (dec ecx).
  Ломало ВСЕ строковые конкатенации с сужением CHAR->SHORTCHAR
  (`SHORT("..." + x)`, SHORTCHAR-конкат), в т.ч. LinRegistry.LoadKV.
- `GenStringComp`: 46H (inc esi), 47H (inc edi) -> `48 FF C6`, `48 FF C7`.
  Ломало сравнения строк с конверсией (CHAR = SHORTCHAR-литерал).
- `GenDiv`: 2× `48H` (dec eax, коррекция частного при отрицательном
  остатке) -> `FF C8` (+`66` для Int16) с поправкой jns-смещения 1->2/3.

Прецедент: коммит e2abc9e9 уже чинил тот же класс в GenSub
("FF /0,/1 for reg inc/dec (one-byte 40-4F are REX prefixes!)").

## Как искать

```
grep -n 'GenByte(4[0-9A-F]H)' Dev/Mod/CPLamd64.odc.txt Dev/Mod/CPCamd64.odc.txt Dev/Mod/CPVamd64.odc.txt
```
Легальные случаи — настоящие REX-префиксы (48/49/4C/4D перед BB/89/8D...).
Подозрительны 40-47, 4F и комментарии вида `(* inc/dec eXX *)`.

Правильные 64-битные формы: inc r64 = `REX.W FF /0` (48 FF C0+r),
dec r64 = `REX.W FF /1` (48 FF C8+r), для 32-бит: FF C0+r / FF C8+r.

## Ловушка №2: смещения коротких прыжков при замене инструкций

При замене 1-байтовой инструкции на 2-3-байтовую ВСЕ ручные смещения
коротких переходов (jns/je +N), перепрыгивающие через неё, должны быть
пересчитаны. GenDiv: jns +5 пропускал `or(2)+je(2)+dec48(1)`; после замены
dec на `FF C8`(2) нужно +6 — оставили +5, прыжок приземлился на ВТОРОЙ байт
`FF C8` = 0xC8 = `enter 0x558b,-4` (enter с nesting level 28 толкает рамку
и роняет rsp на десятки КБ — с виду "спонтанная смена контекста без сигнала").

Диагностика: пошаговый трейс rip/rsp/rbp в gdb (stepi в цикле while);
момент, когда rsp/rbp меняет "невозможная" инструкция = rip показывает на
середину инструкции => кто-то прыгнул не туда => ищем короткий переход
с устаревшим смещением.

Правило на будущее: правишь длину эмитируемой инструкции — grep'ай все
GenByte-смещения (79H/74H/75H/ebH ...) в радиусе этой процедуры генератора.
