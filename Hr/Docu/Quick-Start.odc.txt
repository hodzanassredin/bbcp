Herschel partially supports the traditional compiler interface. Commands
	HrCompiler.Compile
	HrCompiler.CompileSelection
operate on the focus text window: a MODULE is expected in the beginning of the text, or, if there is a selection, in the beginning of the selection.

File and directory structure:
ATTN! Herschel does not mess with your standard BlackBox module files. Instead, code, symbol, and linked executable files are stored under Hr/Demo. The notion of subsystem is not supported at the time, which means all module files are kept in the same directory (by file type).

Here is a convenient tool to try out Herschel. You may edit a trial module right in this document, then use HrCompiler.ShowDecoded to see the disassembly of the compiled module along with other metainformation

As you experiment with Herschel, keep in mind it is work in progress ).


HELLO WORLD

The following is a classic HelloWorld example, with a somewhat more meaningful message. To run it, first compile the Libc module, which is the interface to host console output functions; then run the module Albert.

Instructions:

1. Select each MODULE and call HrCompiler.Compile.
There should be a positive report in the log "compiled successfully'.


(* Not just a Hello World in Windows *)

MODULE User32 ["user32.dll"];
	TYPE PtrSTR = POINTER TO ARRAY [untagged] OF SHORTCHAR;
	PROCEDURE [ms64] MessageBoxA* (hwnd: LONGINT; msg, title: PtrSTR; buttons: LONGINT);
END User32.

MODULE Kernel32 ["kernel32.dll"];
	PROCEDURE [ms64] ExitProcess* (code: LONGINT);
END Kernel32.

MODULE WinHelloWorld;
	IMPORT User32, Kernel32;
BEGIN 
	User32.MessageBoxA(0, "Hershel's BlackBox", "Make it as simple as possible, but not simpler", 0); 
	Kernel32.ExitProcess(0);
END WinHelloWorld.

(* Not just a Hello World in Linux *)

MODULE Libc ["libc.so.6"];
	TYPE PtrSTR = POINTER TO ARRAY [untagged] OF SHORTCHAR;
	PROCEDURE [sysv] puts* (s: PtrSTR): LONGINT;
	PROCEDURE [sysv] exit* (code: INTEGER);
END Libc.

MODULE Albert;
	IMPORT Libc;
	VAR s: ARRAY 64 OF SHORTCHAR; res: LONGINT;
BEGIN
	res := Libc.puts("Albert asked to make it as simple as possible, but not simpler.");
	s := "Ann is awesome";
	res := Libc.puts(s);
	Libc.exit(28)
END Albert.


2. Prepare executable 

for Windows
"HrPeFmt.Install; HrCompiler.ModuleTo('WinHelloWorld', 'pe')"

for Linux

"HrElfFmt.Install; HrCompiler.ModuleTo('Albert', 'elf')"


3. Run

in Windows
"Dialog.RunExternal('Hr/Demo/Elf/WinHelloWorld.exe')"


in Linux
"Dialog.RunExternal('wine Hr/Demo/Elf/WinHelloWorld.exe')"

"Dialog.RunExternal('./Hr/Rsrc/startElf ./Hr/Demo/Elf/Albert')"

program run with loader /lib64/ld-linux-x86-64.so.2
direct call cause segmentation fault in modern linux systems
there is the issue to work on this problem



MAKING A DLL

1. Write your Component Pascal module and compile it with HrCompiler.Compile. This should produce the .ocf file for your module under Hr/Demo/Code.

2. Replace M with your module's name in the following example and run it:
"HrPeFmt.Install; 
HrBinder.OcfTo('Hr/Demo/Code/', 'M.ocf', 'Hr/Demo/Elf/', 'M.dll', 2, FALSE)"

This should produce the DLL for your module under Hr/Demo/Elf.

!! Most of the time, exported procedures that are to be called by DLL importers, need to be compiled for the Microsoft 64-bit calling convention. This requires [code] system flag for your procedure, which becomes available when you import SYSTEM, for example:
	MODULE M;
		IMPORT SYSTEM;
		
		PROCEDURE [ms64] P* (VAR x: INTEGER);
		BEGIN x := 1978
		END P;
	END M.
